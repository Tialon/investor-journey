# IoT与平台集成：区分接入、状态与业务确认

> 学习参考，练习未执行。用阿里云 IoT/OSS 和微信小程序、微信支付 APIv3 举例。SDK、地域、产品实例及接口版本均敏感；接入前按实际账号能力重新核对。

## 核心解释

### IoT SDK、AMQP与物模型各自负责什么

设备 SDK 常负责设备身份认证、连接维护、消息收发与协议封装；云端 SDK 调用设备管理、属性查询或指令接口；AMQP 服务端订阅则把平台收到的设备消息交给业务服务器消费。三者处于不同位置，不能因为都叫 SDK 就混用凭证或连接参数。设备接入成功，也不等于业务服务器已经订阅正确的消息类型。[平台功能](https://help.aliyun.com/zh/iot/product-overview/features)、[AMQP客户端接入](https://help.aliyun.com/zh/iot/developer-reference/connect-an-amqp-client-to-iot-platform)。

物模型将设备能力描述为属性、事件与服务：温度是属性，过温告警是事件，设置目标温度可建模为服务或可写属性。标识符、数据类型、单位、范围及版本是协议契约，收到数字 `25` 之前要知道它是摄氏度还是其他口径。[定义物模型](https://help.aliyun.com/zh/iot/user-guide/add-a-tsl-feature)。

建议链路为“设备上报 → 平台校验与转发 → 消费者校验 → 持久化事件 → 更新状态视图”。消费成功确认要以处理结果为依据；连接重建、重复消息、消费者崩溃与乱序都要有策略。可以用设备标识和业务消息 ID 建唯一约束，并记录设备发生时间、平台接收时间、业务入库时间。消息 ID 的作用域与重投规则要核对平台文档，不能假定全局唯一。[通信问题与重复消息](https://help.aliyun.com/zh/iot/support/faq-about-messaging)。

### 属性快照不是事件历史

`QueryDevicePropertyStatus` 用于查询设备或孪生节点的属性快照。快照适合首页展示当前已知温度、最后状态和更新时间，不能据此还原所有告警与每次变化；不同属性的更新时间还可能不同，整个对象不必然是同一时刻的原子照片。[属性快照API](https://help.aliyun.com/zh/iot/developer-reference/api-querydevicepropertystatus-2018-01-20)。

若设备先上报序号 102，再迟到序号 101，不能按“最后收到”直接覆盖成旧状态。按属性定义单调序号或可信时间的比较规则，保留原始事件供追查；设备重启后的序号重置需要启动批次或其他纪元信息。设备时钟可能漂移，未知时应保留不确定性，而不是强行修正成看似完整的历史。云端指令受理成功也不等于设备执行成功，应记录指令 ID、响应和超时后的查询。

## OSS与内容安全的场景和边界

OSS 保存对象，业务数据库保存归属、版本、审核状态等元数据。大文件直传可减少应用服务器中转，但客户端只能拿限定对象前缀、动作和时效的 STS 临时凭证或预签名 URL；长期 AccessKey 留在服务端。签名地址本身代表临时权限，不能当作可随意公开的普通链接。[STS授权访问](https://help.aliyun.com/zh/oss/developer-reference/use-temporary-access-credentials-provided-by-sts-to-access-oss)。

“上传成功”只说明存储环节成功，不能同时推导文件属于当前用户、格式可信或审核通过。可设计 `UPLOADED → REVIEWING → APPROVED/REJECTED` 状态，审核绑定对象版本或摘要，避免同名对象被替换后继续沿用旧审核结论。失败和超时保留待处理状态，再由重试或人工复核收敛。

内容安全服务返回标签、置信分或处置建议，具体取决于产品版本；应用仍需定义审核阈值与人工复核流程。HTTP 成功不等于“内容安全”，机审也不是绝对正确。1.0 与增强版接口域名、结果字段、服务选择不同，不可把旧版字段直接套到新版。[版本对比](https://help.aliyun.com/zh/document_detail/2539430.html)、[图片审核接入](https://help.aliyun.com/zh/document_detail/467828.html)。

## 微信登录与支付确认

小程序前端调用 `wx.login` 得临时 `code`，传给业务服务端；服务端使用应用凭据调用 `code2Session` 换身份和会话信息，再建立自己的登录态。微信身份标识不等于本系统管理员权限；AppSecret、session_key 不应下发给前端。不同 AppID 的身份映射与账号绑定要单独设计。[微信官方类型定义中的登录说明](https://github.com/wechat-miniprogram/api-typings/blob/master/types/wx/lib.wx.api.d.ts)。

支付链路应由服务端计算可信订单金额并下单，前端负责调起与展示。前端回调可能缺失、重复或被伪造，不能仅凭它发货。服务端接收支付通知时，使用原始请求体与通知头完成验签、解密，核对商户、应用、订单号、币种、金额及交易状态，再以数据库条件更新或唯一约束推进一次订单状态；超时和通知缺失通过主动查询、对账补偿。通知重复到达时返回已处理结果，不能重复发货。[微信支付官方Java SDK：回调通知与订单查询](https://github.com/wechatpay-apiv3/wechatpay-java)。

## 常见误区与一句话面试回答

常见误区是把平台受理当业务完成、把快照当全量历史、把 SDK 验签当整个订单业务都正确。SDK 减少协议细节，业务仍需校验语义、处理重复与补偿。

**一句话回答：** 平台集成要区分身份认证、消息到达、状态更新与业务成功，使用可追踪标识、幂等状态机和可核查的服务端结果收敛不确定性。

## 实操练习（未执行）

无需真实设备、云账号或支付扣款，先在本地编写纯逻辑模拟器：

1. 准备三条 JSON 消息：`{"device":"d1","boot":"b1","seq":102,"temp":26}`、同一条重复消息、`{"device":"d1","boot":"b1","seq":101,"temp":24}`。加入唯一事件键和条件更新，执行后分别打印事件表与状态表；验证重复不重复计数、旧事件保留但不覆盖新状态。
2. 为文件创建 `objectKey/version/status` 三字段记录，依次模拟上传、审核超时、审核通过、同名替换；断言旧审核结果不能批准新版本。画出失败重试与人工复核入口。
3. 用支付官方 SDK 的测试样例或本地生成的测试密钥验证通知解析；覆盖签名错误、金额不符、同一通知两次、数据库已提交但响应丢失、通知缺失后查单这五类情况。只使用测试数据，模拟回调不等于完成真实支付验收。

应产出：消息契约、状态迁移图、输入与实际输出、幂等断言和失败恢复记录；尚未执行的检查不得勾为通过。
