# Spring AI：对话链、流式响应与工具调用

本篇关注怎样把模型接入可追踪的业务流程。资料核验日期：**2026-10-20**。Spring AI 的动态 reference 当日展示 2.0.1；Advisors、工具循环和结构化输出的 API 有版本变化，学习时先核对项目 BOM、依赖树和对应版本文档，不能据此推断现有工程版本。

适用场景包括需要会话追问的知识问答、实时生成与进度推送、结构化字段提取，以及受权限约束的业务工具接入；这些能力可组合使用，但应分别设计失败和完成状态。

## 1. ChatClient 与 Advisors：一次回答经过哪些步骤

`ChatModel` 面向模型调用，`ChatClient` 提供组织提示词、调用方式和输出转换的上层接口。业务可将重复动作放入 Advisor：日志记录调用信息，记忆补充本轮需要的对话，RAG 补充检索证据，结果记录保存执行状态。Advisor 是调用链上的拦截和增强机制；较小 order 先处理请求、后处理响应，因此位置决定它看到的是原始问题还是补全后的提示词。[官方 ChatClient](https://docs.spring.io/spring-ai/reference/api/chatclient.html)、[Advisors](https://docs.spring.io/spring-ai/reference/api/advisors.html)

例如“这个方案为什么更贵”需要上一轮的方案指代，也需要当前报价文档。记忆解决对话连续性，RAG 提供外部资料，两者职责不同。记忆必须以可信身份下的会话标识隔离；窗口记忆可能丢弃旧消息，不能直接充当完整聊天档案。RAG 增强也不会自动保证答案正确或来源有权访问。[官方 Chat Memory](https://docs.spring.io/spring-ai/reference/api/chat-memory.html)

工程上可为一次逻辑请求建立 `requestId`，记录租户、会话、提示词版本、模型标识、引用文档版本、耗时、用量与结束原因。日志重在排查，业务结果表重在可查询和状态一致；默认避免输出密钥、完整个人信息和整份上下文。流式回答应区分 `started/completed/failed/cancelled`，收到几个片段不能记成成功。重试还应区分逻辑请求与调用尝试，避免重复落结果。

可以先画出“可信身份与数据范围→读取会话→构造检索查询→取回证据→模型→校验和记录”的设计草图，再决定哪些步骤放入 Advisor，哪些留在业务服务。顺序没有适合所有项目的固定答案：追问检索可能需要上一轮指代，但整段历史直接拼进查询又可能引入噪声；记录最终答案与观察原始模型响应也可能需要不同位置。关键是为每一步标注输入、输出和失败后状态，而不是只罗列 Advisor 名称。

上下文预算同样需要显式分配。对话越长，历史、检索资料和工具结果越容易挤占输出空间；应按任务选择窗口、摘要或裁剪策略，并保留来源标识。摘要可能丢失条件，裁剪可能丢掉否定句，因此缩短文本后仍需用边界样本检验。

**一句面试回答：**ChatClient 组织模型请求，Advisor 复用记忆、RAG 和观测等横切逻辑；应明确链顺序、会话隔离与完成状态，使回答能够追踪和复现。

## 2. SSE：持续交付答案，不等于任务生命周期

SSE 在 HTTP 响应上持续发送 `text/event-stream` 事件，适合模型逐段输出和任务进度；它主要是服务端向客户端推送，双向实时交互可评估 WebSocket。事件的 `id`、`event`、`data` 和空行分隔由协议定义；浏览器重连能力也不等于业务已经实现断点续传。[WHATWG SSE 标准](https://html.spec.whatwg.org/multipage/server-sent-events.html)

应用协议可定义 `delta`、`citation`、`done`、`error`，其中 `done` 表示业务完整结束，不能仅靠 HTTP 200 判断成功，因为状态码发出后生成仍可能失败。反向代理缓冲、空闲超时、心跳和慢消费者都影响体验；无限缓存片段会把客户端慢的问题转成服务端内存问题。首字延迟与总耗时应分别观察。

**断开 SSE 不保证远端模型停止生成或停止计费。** 浏览器、网关、应用、SDK、供应商之间有多段连接，取消必须逐层传播；还要核对供应商是否支持取消及其计费规则。实践中同时设置总超时、输出上限、并发预算，记录取消原因和最终可获得的用量，不将客户端断连推断为零成本。

**一句面试回答：**SSE 改善的是结果交付方式；我仍需设计结束事件、重连语义、流量控制和取消传播，并单独核验远端生成与计费状态。

## 3. 结构化输出：格式校验之后还有业务校验

将文本转换为 Java record 或 DTO，适合意图分类、字段提取和工作流路由。提示词约束加转换器通常只是尽力生成与解析；供应商原生 schema 约束也需要确认模型和接口支持，且都不能证明字段内容真实。[官方 Output Converters](https://docs.spring.io/spring-ai/reference/api/structured-output/converters.html)

例如输出 `{ "intent": "REFUND", "orderId": "123" }`，JSON 合法之后仍要检查枚举、必填值、长度与订单归属。若缺少信息，应允许 `UNKNOWN` 或澄清结果，避免被迫猜测。流中的半截 JSON 不适合直接驱动操作；应等完整对象通过 schema 和业务校验后再消费。有限重试可修复格式，但要限制次数和预算，不能把重复生成当成事实核验。

**一句面试回答：**结构化输出把自然语言变成可校验的数据契约；schema 检查格式，业务规则检查范围与权限，二者都通过才进入后续流程。

## 4. Function / Tool Calling 与 MCP 的分工

Tool Calling 的典型循环是：应用公布工具描述和参数 schema，模型提出工具名称及参数，应用验证并执行，再把结果返回模型继续生成。模型并不直接拥有数据库连接或业务权限；即使框架支持自动执行，模型产生的参数仍应按不可信输入处理。[Spring AI Tool Calling](https://docs.spring.io/spring-ai/reference/api/tools.html)

“查询订单”和“申请退款”要分开设计。查询工具做身份与数据范围校验；退款工具还需授权、金额校验、幂等键和业务状态检查。模型重复调用、网络超时后的未知结果、工具报错都要有明确处理，不能把错误文本包装成成功。工具结果也可能包含诱导指令，应作为数据使用，不允许它提升自身权限。

MCP 规定宿主、客户端与服务端之间如何协商能力并交换工具、资源等信息：AI 应用是 host，其 client 连接对应 server；server 暴露能力或适配后端系统。它有助于复用接入协议，**不是 LLM，也不替代授权、访问控制和业务规则**。协议版本、传输方式及 Spring AI starter 配置需按实际依赖核对。[MCP 架构（2025-06-18 版本）](https://modelcontextprotocol.io/specification/2025-06-18/architecture/index)、[MCP 工具安全要求](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)

**一句面试回答：**Tool Calling 让模型建议调用工具，应用负责授权执行；MCP 将工具连接标准化，权限与幂等仍由宿主和服务端共同落实。

## 5. 实操练习与验收成果

以下练习**尚未执行**，只作为个人学习任务；先用模拟模型和只读假数据，不接入真实支付。

1. **还原调用链。** 画出日志、会话记忆、检索、模型、结果记录的顺序，为两个会话输入相同追问。验收：提交时序图和脱敏 trace，证明会话不串用，并能解释日志处于不同位置时的内容差异。
2. **制造流式故障。** 模拟五个片段后报错、客户端中途断开、客户端慢速读取。验收：保存事件样本和状态表，成功有唯一 `done`，失败不会标成功；记录取消到达哪些层及尚不能证明的远端状态。
3. **校验工具边界。** 提供只读订单工具与模拟退款工具，输入非法枚举、他人订单、重复幂等键及伪造工具结果。验收：形成用例表，非法请求无业务副作用；完整对象校验后才执行；未知执行结果能查询确认而非盲目重试。
