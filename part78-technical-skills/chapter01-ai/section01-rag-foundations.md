# RAG：为什么引入、何时适用与何时不用

> 学习参考，资料核验日期：2026-10-20。下文是设计分析与待执行练习，不代表个人项目经历或实测结果。

## 核心原理：给本次回答提供可追溯证据

大模型通过训练把语言规律和部分事实压进参数，但通常无法直接读取企业刚发布的制度、内部接口文档或私人笔记。把文件上传到某个系统，也不意味着模型已经学习了文件。RAG 在回答前检索外部资料，把选中的片段作为本次输入，让模型围绕这些证据组织答案。原始 RAG 研究将模型参数与外部可检索记忆结合，关注知识密集型任务及知识更新、来源追踪问题。[RAG 原论文](https://arxiv.org/abs/2005.11401)

可以把链路拆为两个生命周期：离线将资料解析、分块、补充元数据、生成索引；在线把问题改写为检索条件，过滤可访问资料，召回、融合或重排，再构造上下文并生成带出处的回答。离线更新不必重训生成模型，但仍有解析、嵌入、索引发布、缓存失效等成本。RAG 也不限于向量库：倒排检索、关系数据库、全文搜索或混合方案都能提供证据。

例如，用户问“现行退款时限是多少”，模型记忆可能停在旧规则。系统应先限制产品、适用人群、文档生效时间与权限，再找到正式条款，而不是让旧版宣传稿和新制度共同争夺高分。若问题要求历史规则，则应按指定时间检索。版本选择是业务规则，不能交给向量相似度暗中决定。

## 场景与选择：先判断缺的是知识还是执行能力

| 需求 | 优先思路 | 判断理由 |
| --- | --- | --- |
| 内部手册问答、技术文档导航 | RAG | 资料变化且需要出处，原文有可回答证据 |
| 二十页稳定资料的一次性总结 | 直接提供上下文并核对 | 可先评估全文输入，未必值得维护索引 |
| 查某订单当前状态、算实时库存 | 授权 API / SQL 工具 | 状态与计算应由权威系统产生 |
| 固定格式、语言风格、分类习惯 | 提示词、规则或微调 | 缺口可能在行为一致性，而非文档知识 |
| 严格金额汇总、复杂跨表统计 | 数据查询与确定性计算 | 找到相似描述不能保证数字计算正确 |
| 无可靠资料的开放推理 | 模型能力与人工核验 | 检索无法创造不存在的证据 |

这些方案可以组合。例如先调用订单 API 得到事实，再检索退款条款解释规则。微调也可改善领域表达或检索器适配，但不自动保证知识及时、引用真实或权限正确。选择时先建立少量真实问题及标准证据，再比较简单基线和复杂方案，避免为了使用向量库而引入整条链路。

## 边界：检索相关不等于回答正确

相似度描述表示空间中的接近程度，不是事实正确率。一个谈论“退款期限”的旧文档可能比现行规则更像用户问法；“支持退款”和“不支持退款”也可能共享大量词语。不同模型、距离指标与语料下的分数不能直接横向比较，更不能把 0.8 解释为“八成可信”。阈值应由标注样本决定，并同时观察漏答和误答。

RAG 的失败至少有三层：原文缺失或本身错误；正确证据没有进入最终上下文；证据进入后被模型误读或过度推断。换大模型只能改善其中部分问题。原始资料与新证据冲突时，应回到原文位置、发布日期、生效范围及发布主体，明确指出冲突；不能以“检索分高”裁定哪篇是真理。

长上下文也并非证据越多越好。《Lost in the Middle》在其测试任务中观察到模型利用信息的能力受上下文位置影响；这提示需要评估片段顺序和噪声，而不是把结论泛化成所有模型必然无法读取中间内容。[研究原文](https://arxiv.org/abs/2307.03172)

工程上还需面对检索延迟、重排算力、上下文 token 成本、引用映射和知识更新。父子块能补足上下文，却可能把无关章节重新带入。文档中的指令属于待分析内容，应与系统指令隔离；检索前完成租户和权限过滤，回取父块时再次核验，不能先把受限内容交给模型再要求它保密。没有足够证据时应返回“资料不足”或请求补充条件。

## 最小可用实现与验收

建议先用清晰文本、小规模语料和单路检索建立基线，保留 `source_id / version / effective_at / locator / permission_scope`。每个答案附稳定来源和原文位置，便于人点击复核。加入融合、重排、问题改写前，先记录基线在哪类问题失败，再用同一测试集验证收益与额外开销。

Spring AI 可通过 Advisor 接入检索与上下文增强；其模块支持把检索、后处理和生成分开配置。框架负责连接流程，文档治理、权限策略和答案验收仍需应用明确设计。[Spring AI RAG 官方文档](https://docs.spring.io/spring-ai/reference/api/retrieval-augmented-generation.html)

**版本敏感：**资料核验时 Spring AI 页面显示 2.0.1；Advisor 类名、构造方式及默认行为应以项目实际 BOM 版本为准。本文不要求升级，也不把示例阈值当作生产默认值。

## 一句话面试回答

RAG 在回答前检索外部证据，适合需要私有知识、及时更新和出处的问答；它不能保证检索结果或生成结论正确，必须结合文档版本、权限、证据核对与拒答机制。

## 实操练习与预期成果（未执行）

1. 自建十篇无隐私的制度样例，其中两篇是过期版本，准备二十个问题，覆盖可回答、无答案、时间条件和相互矛盾情形。
2. 比较“仅模型回答”“全文上下文”“单路检索 RAG”，保持问题及生成配置一致，逐条记录答案、引用和耗时；先人工判定证据是否足够。
3. 加上生效时间过滤与资料不足拒答，再比较误用旧版本、无依据补充、漏掉例外条款的数量。
4. 将一次失败定位到原文、解析、检索、上下文或生成环节，写出一个可验证的修复假设。

预期成果：一份问题—标准证据表、一份对比记录、一个失败案例复盘。完成标准是能解释差异的来源；本文未运行模型、建立索引或报告任何准确率。
