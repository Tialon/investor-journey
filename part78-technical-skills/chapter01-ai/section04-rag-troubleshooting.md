# RAG 排障：开发与生产答案矛盾，怎样逐层溯源

> 学习参考，资料核验日期：2026-10-20。案例均为构造示例；下文是调查方法，不代表发现了真实生产故障。

## 核心原理：先找首次分歧，再解释最终答案

同一句问题在开发说“支持”，生产说“不支持”，只能说明输出不同，不能直接归因于模型幻觉、温度或向量库。实际输入还包含用户身份、对话历史、过滤条件、知识快照、提示词、工具结果与模型配置。排障应沿链路比较中间产物，找到两边首次出现差异的位置，再验证它如何影响答案。

先把争议陈述拆为可核验命题。例如“所有设备均支持远程升级”涉及设备类型、固件版本、发布日期和授权范围；“E102 在固件 2.1 后支持”是另一个命题。两边可能回答了不同范围。先请业务证据定义标准：哪份正式原文、适用时点和例外条件有效。若原文本身冲突，应保留冲突并查发布依据，不能用模型多数投票定真伪。

## 固定一次可比较的请求

为同一问题生成排障标识，保存实际生效的配置指纹：代码版本、环境、租户与角色范围、原始问题及改写问题、对话历史摘要、知识发布版本、解析与嵌入模型 revision、集合与别名、检索过滤、候选数、融合权重、重排模型、提示词版本、生成模型与采样参数。比较配置的最终值，不能只看仓库里的默认 YAML。

完整文本、历史和检索结果可能有敏感信息。优先记录内容哈希、来源标识、版本和定位信息，必要时在受控排障副本中保存已脱敏正文。Spring AI 提供模型、工具和向量存储的观测能力，提示词及输出正文默认不会随意导出，开启相关日志需评估内容范围。[Spring AI 可观测性文档](https://docs.spring.io/spring-ai/reference/observability/index.html)

## 沿链路逐层核对

| 层次 | 比较的证据 | 典型问题与下一步 |
| --- | --- | --- |
| 请求与身份 | 原问、改写、历史、权限和时点 | 同一句短问被不同历史补全；先固定输入 |
| 原文与发布 | 原件哈希、版本、生效范围、知识批次 | 开发新版、生产旧版；查发布与缓存 |
| 解析与分块 | 抽取文本、表格、父子映射、位置 | 例外被切掉或单元格串列；回原件校对 |
| 嵌入与索引 | 模型 revision、归一化、维度、集合 | 文档和问题用不同模型；按快照重放 |
| 召回与过滤 | 各路候选、分数、过滤表达式 | 租户或时间条件不同；逐路比较 |
| 融合与重排 | 去重前后列表、权重、截断 | 正确片段被截断、降序或融合挤走 |
| 上下文与提示词 | 实际消息顺序、token预算、模板版本 | 检索到了但未装入最终请求 |
| 生成与呈现 | 原始输出、工具响应、缓存、UI拼接 | 缓存旧答案或流式重试拼接重复 |

这张表的用途是缩小调查范围。例如两环境最终上下文的哈希已不同，应先解释证据差异；上下文和生成请求都一致，才更值得检查模型提供方、实际模型版本、采样、重试和非确定性。温度设零可以减少部分随机性，但不能跨服务端升级、硬件与算法实现保证逐字重现。

索引也有“写入已确认”与“查询可见”的区别。Milvus 提供不同一致性级别，读取可见性会受所选策略影响；刚导入后立即查询的差异应记录一致性配置与时间，而不是反复修改提示词。[Milvus 一致性文档](https://milvus.io/docs/consistency.md)

## 小例子：正确片段已召回，答案仍然相反

构造两份规则：v1 写“设备支持远程升级”，v2 写“E102 在固件 2.1 后支持，之前不支持”。开发命中 v2 父块，生产返回 v1，第一处分歧是知识快照或过滤，先修复发布。另一种情况是生产也召回 v2，但片段只剩“支持”，条件位于被截断的前半段；此时问题在分块或上下文，不在生成模型能力。

还可能两边都提供 v2 全文，生产提示词却要求无条件给出“是／否”，并把历史中的“固件 1.8”错误改写成“2.1”。应保存改写前后问题并核对。若引用片段没有支持最终断言，属于证据使用或生成问题；若片段支持答案但原文已过期，属于知识治理问题。两种问题不能用同一个“忠实度高”掩盖。

RAGAS 的 Faithfulness 检查回答中的主张能否由检索上下文支持；这有助于发现脱离证据的生成，但不能证明上下文本身最新、真实或业务适用。[RAGAS Faithfulness 定义](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/faithfulness/)

## 修复、回归与常见误区

先制作最小重放：固定原文快照、候选列表或最终上下文，分阶段替换开发与生产组件，一次只改变一个因素。例如固定生产上下文调用开发生成配置，或用相同检索配置搜索同一批索引，观察首次分歧是否随组件移动。重放只能在授权范围内进行，不能把生产原文直接复制进个人测试数据。

修复后除了原失败题，还应检查同义问法、否定问法、历史版本、无答案及权限边界。记录受影响样本和未覆盖范围，再决定发布。不要同时改模型、提示词和权重后只凭一次回答宣布根因；也不要把重建索引当万能方案，未修复解析器时只会稳定地重建错误。

对外回答应提供来源版本、原文位置与适用条件，证据不足时说明不确定。开发和生产答案“更像人话”不构成正确性证据；相似度高、引用存在、自动评估高分也需分别核对。

**版本敏感：**Spring AI 观测属性、Milvus 默认一致性与 RAGAS 指标 API 会随版本变化。排障记录应写实际依赖和生效参数；本文链接用于理解机制，不承诺跨版本配置名完全一致。

## 一句话面试回答

开发与生产答案矛盾时，先固定请求身份、知识快照和实际配置，逐层比较解析、召回、重排、最终上下文和生成结果，找到首次分歧；有证据冲突则回原文核对版本和适用范围，再用最小重放验证修复。

## 实操练习与预期成果（未执行）

1. 在本地样例里制造三个故障：旧知识版本、例外条款截断、提示词换版；不接入真实生产数据。
2. 为每个故障填写上表，保存各阶段标识及输入输出差异，提出根因和可证伪的预测。
3. 每次只修复一个环节，重放原题，再检查十个相邻问题、一个无答案问题和一个越权问题。
4. 写简短复盘：影响、证据链、首次分歧、修复、回归结果与剩余不确定性；未知项明确标为待查。

预期成果：三份故障定位记录、一份脱敏 trace 样例、一份回归清单。本文未访问生产环境、运行重放或产生真实评估分数。
